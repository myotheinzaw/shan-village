J Where Artifacts stop working

You asked what limitation forces a backend. This is not a theoretical answer — I hit the wall today, twice, while doing your ordinary daily export.

Today's evidence. The nightly job built your roster workbook (13–24 KB) and had to move it into Drive. A file can only reach Drive by passing through this conversation as base64 text. The wastage report — 7 KB — went through cleanly. The roster workbook did not: both attempts corrupted in transit. The wastage report for 25 August is in your Drive folder. The roster snapshot for 25 August is not.

That is a hard ceiling of roughly 8 KB per file, per day, for a single-writer page. Inventory across three locations with photo evidence is an order of magnitude past it.

The five specific limits

LimitWhat it means for inventory
No server, no secrets An Artifact is one HTML file in the viewer's browser. There is nowhere to put a Google service-account key. Anything you embed is readable by anyone with the link — which is exactly what your point 36 forbids.
Every save rewrites the whole page A stock take that adds one line republishes the entire document. Two counters in the Kitchen and the Store pressing save in the same second is a race: one wins, one is rejected. The wastage page survives this because entries are occasional. A month-end count across three locations is a sustained multi-writer workload.
Photos live inside the page The page has a 16 MB ceiling and every photo is carried in every save. A 125-item count with evidence photos exceeds that in one session, and each save gets slower as the count proceeds.
No network access The page cannot call the Drive API, a database, or anything else. Its only outbound action is saving a new copy of itself.
No real identity A shared lock code is not a user. "Counted by" and "Approved by" would be self-declared text. An audit trail you cannot trust is worse than none, because it looks authoritative.

Verdict. The roster and wastage pages are the right tool for what they do: one person editing, small data, no photos of consequence. Inventory is not that shape. Building it as an Artifact would mean faking the parts you explicitly said not to fake — the Drive writes, the Excel sync, the audit trail. Inventory belongs in the web application already sitting in your repository, which was built for exactly this and already contains a disabled inventory module and four inventory permissions waiting to be switched on.

A Proposed architecture

Nothing new is invented here. The roster application already has the shape; inventory becomes a second module inside it.

What holds the truth

Postgres. Every count, transfer, receipt and adjustment is a row. Current stock is derived from movements, never typed in — so it can always be explained.

What Drive holds

Photographs and generated Excel files. Drive is the document repository and the thing you open on a laptop. It is never the database.

Where the secrets live

Only in Vercel's server environment. The browser never sees the service-account key, and never talks to Drive directly.

Who you log in as

The same Supabase account as the duty roster. One person, one login, both modules — as you asked in point 21.

Why not Google Sheets as the live source

You offered it as a fallback. I would not take it. A sheet has no row-level security, no transactions and no foreign keys — three counters editing at once will corrupt each other, and nothing stops a stock taker reading the cost of every item. Postgres gives all three, and the Excel file is generated from it, which is what you actually want: the spreadsheet as an output, not as the system of record.

B Database schema

New tables only. Everything else — profiles, roles, permissions, outlets, audit_logs, app_settings, import_batches — already exists and is reused.

Locations

Your three locations are stock locations, not restaurant outlets, so they get their own table rather than being forced into outlets. A location can later belong to an outlet.

-- Al Ghurair Kitchen · Al Ghurair Store · Al Quoz Home
create table inv_locations (
  id uuid primary key, code text unique, name text,
  kind text,                    -- kitchen | store | home
  outlet_id uuid null references outlets(id),
  is_active boolean default true, sort_order int
);

Item master

create table inv_categories (id uuid pk, name text, parent_id uuid null, sort_order int);
-- self-referencing: category and subcategory in one table, admin-editable

create table inv_items (
  id uuid pk,
  sku text unique,              -- your Item ID
  name text not null,
  category_id uuid, brand text, supplier_id uuid null,
  purchase_unit text,           -- how you buy it     e.g. case
  count_unit text,              -- how you count it   e.g. bottle
  conversion_factor numeric,    -- 1 case = 12 bottles
  unit_cost numeric,            -- current cost, per count_unit

create table inv_item_levels (
  item_id uuid, location_id uuid,
  min_level numeric, reorder_level numeric, max_level numeric,
  primary key (item_id, location_id)
);

Movements — the heart of it

One ledger, every reason. Receipts, transfers, usage, wastage, adjustments and count corrections are all rows in inv_movements. Current stock is the sum. This is what makes point 7 (opening → closing) and point 25 (valuation) fall out for free instead of needing separate machinery, and it is why a number can always be traced to the document that caused it.

create table inv_movements (
  id uuid pk,
  item_id uuid, location_id uuid,
  qty numeric not null,         -- signed: +receipt, −issue
  unit_cost numeric,            -- cost at the moment it moved
  kind text not null,           -- opening | receipt | transfer_in | transfer_out
                                -- usage | wastage | adjustment | count
  source_table text, source_id uuid,   -- the GRN, transfer or stock take behind it
  occurred_at timestamptz, created_by uuid, note text
);
create index on inv_movements (item_id, location_id, occurred_at);

-- Read model, refreshed on write. Never edited by hand.
create materialized view inv_current_stock as
  select item_id, location_id, sum(qty) as qty,
         sum(qty * unit_cost) as value
  from inv_movements group by 1, 2;

Stock takes

create table inv_stock_takes (
  id uuid pk,
  ref text unique,              -- ST-20260825-001
  location_id uuid, take_date date,
  status text,                  -- draft | in_progress | submitted | reviewed
                                -- | approved | locked
  started_at timestamptz, completed_at timestamptz,
  counted_by uuid, reviewed_by uuid, approved_by uuid,
  is_month_end boolean default false,

);
create unique index on inv_stock_takes (location_id, take_date)
  where status <> 'cancelled';   -- point 30: one count per location per day

create table inv_stock_take_lines (
  id uuid pk, stock_take_id uuid, item_id uuid,
  counted_qty numeric null,       -- NULL = not counted, 0 = confirmed empty
  count_unit text, system_qty numeric,   -- frozen when the count starts
  unit_cost numeric,
  variance_qty numeric generated, variance_value numeric generated,
  status text,                  -- matched | minor | shortage | excess | review
  note text, variance_comment text,
  counted_by uuid, counted_at timestamptz
);

Point 29 is a nullable column, not a convention. counted_qty is NULL until somebody counts, and 0 only when they confirm the shelf is empty. The database enforces the difference, so no later query can blur it.

The audit trail is not a new table: the platform's existing audit_logs already records actor, action, before, after, timestamp and reason, and inventory writes to it like every other module. Point 19 is satisfied by reuse, and the Audit Log page you already have gains an inventory filter.

C Google Drive integration

You are right that a shared folder URL grants nothing. Here is what actually authorises the write.

Method: a Google service account

  1. Create a Google Cloud project and enable the Google Drive API.
  2. Create a service account. Google issues an email such as shan-village-inventory@….iam.gserviceaccount.com and a JSON key.
  3. Share your Drive folder with that email address, as Editor. This is the step that grants permission — the folder itself does the granting, so you can revoke it at any time from Drive without touching the application.
  4. The JSON key goes into Vercel's environment variables. It is never sent to a browser, never committed to the repository, and never appears in the page source.

Why not OAuth

OAuth uploads as a person and needs that person to re-consent periodically. A month-end job must run at 8pm whether or not anyone is logged in.

Why not Apps Script

Workable, but it puts half the logic in a second place with its own editor, quotas and deployment. One backend is easier to keep correct.

How a photo actually travels

  1. The phone captures it and shrinks it in the browser — the same technique already proven in your wastage page, which turned 586 KB into 54 KB while staying readable.
  2. It is sent to the app's own server route, not to Google.
  3. The server uploads it to Drive with the service account, creating the year, month, location and date folders if they are missing.
  4. The returned Drive file id and URL are written to inv_photos against the count line.
  5. If the upload fails the row stays pending and a retry job picks it up. The count is never blocked by a photo, and a photo is never silently lost.

E Roles and permissions

The platform already has roles, permissions, per-user overrides and a modules table. Inventory adds permission keys; it does not add a second access system.

Your repository already carries an inventory module row marked "Not yet available" and four permissions — inventory.view, inventory.count, inventory.adjust, inventory.value_view — seeded inactive. That was deliberate groundwork for this module. Phase 1 activates them and adds the rest.

RoleCan doKey permissions
Owner / AdminEverything, including reopening a locked count and changing costsall
Inventory AdminItem master, receipts, transfers, counts, approval, all reportsinventory.* except reopen
Location SupervisorCounts and operations for their own locations; reviews variancecount, review, transfer.request
Stock TakerEnter counts and photos. No costs, no approval count only
View OnlyRead what they are entitled to see view

Two things worth deciding deliberately

Cost visibility is its own permission. inventory.value_view is separate from inventory.view, so a stock taker counts 8 bottles without seeing that they are worth AED 340. The existing schema already flags it as sensitive.

Supervisors are scoped to locations. A new inv_user_locations table assigns people to locations, and row-level security enforces it in the database — not merely by hiding menus. This is the same principle the roster module was built on: the wall is in Postgres, the menu is only a convenience.

F Inventory workflow

A stock take, end to end

  1. Open — supervisor picks location and date. If a count already exists for that pair the system refuses and offers to continue it; only an admin can authorise a second (point 30).
  2. Freeze — every active item for that location becomes a line, and today's system quantity is copied onto it. The count is judged against the stock as it stood when counting began, so a delivery arriving mid-count cannot create a phantom variance.
  3. Count — on a phone: search or scroll, tap −/+ or type, add a photo, next item. A progress bar reads 42 / 125 counted. Everything is saved as you go.
  4. Submit — the system blocks submission if a rule you configured is unmet: a photo missing on a high-value item, or a comment missing where variance exceeds tolerance (point 28).
  5. Review — supervisor sees only the lines that differ, worst first.
  6. Approve — and only now does anything move: one count movement per varying line, current stock updated, the Excel master regenerated, the approved report filed to Drive, and the record locked.
  7. Reopen — admin only, requires a written reason, and both the reason and the original figures stay in the audit log. Nothing is ever quietly rewritten.

Variance and status

Physical − system, as quantity and as value. Bands are settings, not code — my proposed defaults, for you to confirm or change:

StatusDefault rule
Matchedexactly equal
Minor variancewithin 2% or 1 count unit, whichever is larger
Shortage / Excessbeyond that, negative or positive
Review requiredover 10%, or value beyond a threshold you set

I have deliberately not invented a monetary threshold, a tolerance percentage that triggers investigation, or a valuation method. Those are Shan Village policy with money attached. They ship as configurable settings with the defaults above, and you set them before go-live.

Stock status

Recomputed on every movement: Out of stock (0) · Critical (at or below minimum) · Low (at or below reorder) · Healthy · Overstock (above maximum). The Attention Required screen lists only the first three.
